# План PaymentService: приём реальных платежей через ЮKassa

## Принятое решение и границы первой версии

- Отдельный Python-сервис с REST API, PostgreSQL и официальным SDK ЮKassa. Один магазин и один провайдер: ЮKassa.
- Сервис хранит платежи и возвраты, создаёт их, отдаёт статусы, принимает уведомления и сверяет незавершённые операции с ЮKassa.
- Деньги и платёжные данные карты проходят через страницу ЮKassa; сервис не принимает и не хранит реквизиты карты.
- MVP — разовая оплата календарного месяца или года выбранного плана подписки: одностадийный платёж с перенаправлением на страницу ЮKassa и автоматическим подтверждением. Продление заранее разрешено; оплаченные периоды хранятся отдельно. В MVP нет смены плана посреди оплаченного периода и частичных возвратов. Автосписания обязательны после MVP отдельным этапом; смена плана посреди периода и частичные возвраты запланированы после MVP. Выплаты, мультимагазин и второй провайдер вне текущего плана.
- PostgreSQL — источник истины для локальных операций. Redis/Celery и RabbitMQ не обязательны: плановые сверки можно запускать отдельным процессом или заданием по расписанию.
- Следующий шаг начинают после выполнения критериев предыдущего. Для каждого шага нужны код, короткая инструкция и указанные проверки; отметка `готово` означает, что проверка реально выполнена.

## 1. Зафиксировать контракт и правила денег

### 1.1. Описать участников и владение данными

Решить, кто создаёт `order_id`, где хранится цена заказа, кто вправе запросить возврат и как Backend узнаёт об успешной оплате. Зафиксировать, что сумма и валюта берутся из доверенного Backend, а не из браузера или Telegram-сообщения.

**Приёмка:** в [документе шага 1.1](.docs/1.1-SCOPE.md) есть схема `Backend → PaymentService → ЮKassa`, список владельцев данных и правило определения суммы; нельзя получить оплату произвольной суммы через публичный клиент.

### 1.2. Описать REST API

Согласовать `POST /payments`, `GET /payments/{id}`, `POST /payments/{id}/refunds`, `GET /refunds/{id}`, `POST /webhooks/yookassa`, `GET /health/live`, `GET /health/ready`. Указать поля запросов и ответов, ошибки, статусы HTTP и требуемую авторизацию. Создание и возврат требуют `Idempotency-Key` от Backend. `POST /payments` возвращает локальный ID, статус и `confirmation_url`; возврат возвращает локальный ID и статус.

**Приёмка:** есть [OpenAPI](.docs/1.2-openapi.yaml) и по одному примеру успешного и ошибочного ответа для каждой операции; внешние клиенты не могут передать `provider_payment_id`, `status` или готовый `confirmation_url` как источник истины.

### 1.3. Описать жизненный цикл

Зафиксировать локальные состояния платежа и возврата `pending`, `succeeded`, `canceled` и отдельное поле `resolution_status=known|unknown` для неясного результата обращения к провайдеру. Указать разрешённые переходы. `confirmation_url` и возврат пользователя на сайт не означают успешную оплату. Решение о статусе продавца, фискализации и составе чека отложить до допуска настоящего магазина (шаг 7.3); для тестового магазина оно не блокирует разработку.

**Приёмка:** таблица переходов и правило выдачи оплаченной подписки записаны в [документе шага 1.3](.docs/1.3-LIFECYCLE.md); выдача возможна только после подтверждённого `succeeded`.

## 2. Подготовить сервис и хранилище

### 2.1. Создать каркас приложения

Добавить приложение, закреплённые зависимости, конфигурацию, запуск сервера и health endpoints. В production отсутствие обязательных настроек должно завершать запуск ошибкой.

**Приёмка:** сервис локально стартует одной документированной командой; `/health/live` отвечает, а `/health/ready` не отвечает успешно при недоступной БД; нет секретов в репозитории.

### 2.2. Настроить PostgreSQL и миграции

Создать таблицы `payments`, `refunds` и, при необходимости, `payment_events`. Хранить внутренний ID, ID заказа, сумму в минимальных денежных единицах или точном десятичном типе, валюту, состояние, ID провайдера, ключи идемпотентности, время создания и обновления. Каждый возврат хранит свою сумму и связь с платежом: модель не сводится к флагу `refunded`. Нужны уникальные ограничения на ID заказа/операции, ключ идемпотентности в своей области и ID провайдера. Backend отдельно хранит оплаченные периоды с планом и ссылкой на заказ, чтобы будущая смена плана не требовала замены одной общей даты окончания.

**Приёмка:** миграция применяется на пустой БД и повторный запуск ничего не ломает; две параллельные записи с одинаковым ключом не создают две операции; денежные значения не проходят через `float`.

### 2.3. Настроить секреты и среды

Задать отдельные параметры тестового и настоящего магазина; запретить произвольный `return_url` из API, использовать доверенный адрес или проверяемый allowlist. Секреты получать из переменных окружения/хранилища секретов, не печатать в логах.

**Приёмка:** `.env.example` содержит только фиктивные значения; тестовый режим не может случайно использовать настоящие ключи; CI-проверка и ручной поиск не находят секретов в репозитории и логах.

## 3. Принимать платежи

[Отдельный план этапа 3](.docs/3.PLAN.md).

### 3.1. Защитить внутренний API

Разрешить вызовы создания платежей и возвратов только доверенному Backend через механизм служебной аутентификации; ограничить права, закрыть публичный доступ к административным маршрутам. Отдельно документировать ротацию ключа.

**Приёмка:** запрос без действующих учётных данных получает 401/403; webhook не требует этих данных; тест показывает, что один клиент не может читать чужую операцию, если сервис поддерживает несколько клиентов.

### 3.2. Проверять вход создания платежа

Проверить существование заказа в доверенном источнике, положительную сумму, RUB, допустимую длину описания и соответствие суммы заказу. Зафиксировать неизменяемый снимок суммы заказа на момент создания платежа.

**Приёмка:** неверная сумма, валюта, пустой `order_id` и подмена цены отклоняются до вызова ЮKassa; тесты покрывают границы суммы и точность копеек.

### 3.3. Реализовать локальную идемпотентность создания

Один ключ и одинаковое тело запроса всегда возвращают одну локальную операцию; тот же ключ с другим телом даёт конфликт. Сохранять ключ и отпечаток запроса в БД до сетевого вызова. Для ЮKassa использовать устойчивый ключ, связанный с локальной операцией. Нельзя повторно создавать платёж с новым ключом только потому, что ответ потерялся.

**Приёмка:** последовательные и параллельные повторы дают один локальный платёж и не более одного вызова создания у провайдера; после рестарта поведение сохраняется; разное тело с тем же ключом даёт 409.

### 3.4. Добавить адаптер ЮKassa и создание платежа

Вынести вызовы SDK в один модуль: создать платёж, запросить платёж, создать возврат, запросить возврат. Установить таймауты; записать ID провайдера и `confirmation_url`. Не возвращать успех оплаты при успешном HTTP-ответе о создании.

**Приёмка:** тестовый магазин создаёт платёж и выдаёт рабочий `confirmation_url`; в БД операция остаётся `pending` до подтверждения; ошибки SDK не раскрывают ключи и внутренние детали клиенту.

### 3.5. Разобрать неопределённый результат и повторы

При таймауте/HTTP 5xx помечать операцию `unknown`, затем выяснять статус у ЮKassa и повторять запрос только с тем же ключом, пока действует окно идемпотентности провайдера. После 24 часов не повторять создание вслепую: сначала сверить операцию, иначе передать на ручной разбор. Ограничить число попыток и интервалы.

**Приёмка:** тесты «ответ потерян после создания» и «ЮKassa недоступна» не создают второй платёж; зависшая операция видна оператору и может быть разрешена сверкой.

### 3.6. Отдать статус платежа

`GET /payments/{id}` читает локальный статус, ID и сумму. При необходимости предусмотреть отдельное обновление из ЮKassa для оператора или фоновой сверки, с ограничением частоты.

**Приёмка:** клиент видит `pending` после создания и `succeeded` только после подтверждённого перехода; ответ не содержит секретов или полного ответа провайдера.

## 4. Безопасно обрабатывать уведомления

[Отдельный план этапа 4](.docs/4.PLAN.md).

### 4.1. Принять webhook

Настроить HTTPS endpoint и подписку в кабинете ЮKassa на `payment.succeeded`, `payment.canceled`, `refund.succeeded` и другие события, реально нужные выбранному сценарию. Ограничить размер тела, проверить формат и не доверять переданному статусу.

**Приёмка:** корректный webhook принят; битый/слишком большой запрос отклонён; URL доступен ЮKassa по HTTPS с допустимым TLS.

### 4.2. Подтвердить событие у ЮKassa

По ID из webhook запросить объект через API ЮKassa и сверить его ID, сумму, валюту, принадлежность локальной операции и актуальный статус. Для возврата сверить ID возврата, ID платежа и сумму. Не полагаться только на IP или тело webhook; при недоступности ЮKassa оставить событие для повторной проверки и не переводить платёж в успех.

**Приёмка:** поддельный `payment.succeeded`, чужой ID и неверная сумма не меняют статус; настоящий webhook после запроса API меняет статус; временная ошибка API приводит к повторной обработке или последующей сверке.

### 4.3. Сделать обработку повторов и конкуренции безопасной

Менять состояние в транзакции с блокировкой строки/условным обновлением. Повторное или запоздавшее событие не должно откатывать конечный статус и повторно запускать выдачу товара. Результат для Backend публиковать через устойчивое событие/outbox или другой документированный механизм с повторной доставкой.

**Приёмка:** 10 одинаковых и одновременно пришедших webhook дают одно изменение состояния и одно бизнес-событие; после сбоя между записью статуса и уведомлением Backend событие доставляется повторно; Backend также обрабатывает повтор без второй выдачи.

## 5. Возвраты

[Отдельный план этапа 5](.docs/5.PLAN.md).

### 5.1. Проверять право и размер возврата

Возврат разрешён только авторизованному оператору/Backend для подтверждённого платежа. В MVP возвращать всю сумму исходного платежа; сумма берётся из БД, а не из запроса. Хранить точную сумму операции возврата и резервировать её под блокировкой, чтобы повторные или параллельные запросы не превысили остаток. Это оставляет основу для частичных возвратов после MVP.

**Приёмка:** неавторизованный запрос отклонён; указать произвольную сумму в MVP нельзя; два одновременных полных возврата не резервируют больше оплаченной суммы.

### 5.2. Создать возврат с собственной идемпотентностью

Сохранить локальный возврат и ключ до вызова ЮKassa; отправлять стабильный ключ в API. Таймаут оставляет `unknown`; результат уточняется через API, прежде чем разрешить новое действие. Учитывать частичный и полный возврат, если они нужны бизнесу.

**Приёмка:** повтор, рестарт и потерянный ответ не создают второй возврат; тестовый магазин возвращает деньги; клиент видит локальный статус и ID возврата.

### 5.3. Подтвердить итог возврата

Обрабатывать уведомление о возврате и плановую сверку; освобождать зарезервированную сумму при подтверждённом отказе. Не считать возврат успешным по ответу о принятии запроса, если его статус ещё не итоговый.

**Приёмка:** статусы `pending`, `succeeded`, `canceled` отражают данные ЮKassa; повторные уведомления не меняют остаток; частичный возврат оставляет верный доступный остаток.

## 6. Восстановление, наблюдаемость и эксплуатация

[Отдельный план этапа 6](.docs/6.PLAN.md).

### 6.1. Добавить плановую сверку

Периодически опрашивать у ЮKassa все локальные `pending` и `unknown`, а также недавние завершённые операции в пределах согласованного окна. Обнаруженные расхождения исправлять по правилам переходов, нерешённые выводить оператору. Сверять платежи и возвраты отдельно.

**Приёмка:** пропущенный webhook не оставляет платёж навсегда `pending`; тест с выключенным endpoint и последующим запуском сверки приводит к верному статусу; расхождения фиксируются и видны оператору.

### 6.2. Добавить безопасные логи и метрики

Логировать correlation ID, локальный ID, ID ЮKassa, операцию, итог и класс ошибки без секретов, персональных данных и полного тела webhook. Метрики: ошибки API, возраст `pending`/`unknown`, отставание сверки, ошибки доставки событий, неразрешённые расхождения.

**Приёмка:** по ID можно проследить операцию; тестовые ошибки вызывают метрики/оповещение; просмотр логов подтверждает отсутствие ключей и реквизитов.

### 6.3. Настроить резервное копирование и восстановление

Делать резервные копии PostgreSQL и проверять восстановление в отдельной среде. Задать сроки хранения, доступ к копиям и порядок действий после потери БД или недоступности ЮKassa.

**Приёмка:** выполнено пробное восстановление; записаны фактические RPO/RTO; восстановленные операции сверены с тестовым магазином ЮKassa без повторного списания.

### 6.4. Подготовить сборку и развёртывание

Собрать минимальный контейнер, миграции запускать отдельным шагом, включить HTTPS на входе, ограничить сетевой доступ к БД и внутреннему API. Зафиксировать версии зависимостей, запуск с непривилегированным пользователем, проверку уязвимостей и откат релиза.

**Приёмка:** стенд разворачивается по инструкции из чистой среды; секреты приходят извне; при ошибочной миграции релиз останавливается; проверен откат приложения и восстановление БД.

### 6.5. Подготовить инструкции оператору

Описать разбор `unknown`, зависших `pending`, неверной суммы, пропавших уведомлений и спорных возвратов. Оператор не должен исправлять статус вручную без сверки с ЮKassa; каждое ручное действие записывается в аудит.

**Приёмка:** другой разработчик по инструкции находит тестовую зависшую операцию, сверяет её и документирует результат без доступа к исходному автору сервиса.

## 7. Проверить перед настоящими деньгами

[Отдельный план этапа 7](.docs/7.PLAN.md).

### 7.1. Автоматические проверки

Покрыть расчёт денег, переходы статусов, идемпотентность, конкуренцию, webhook, таймауты и возвраты. Использовать управляемые ответы провайдера; интеграционные тесты запускать на отдельной PostgreSQL.

**Приёмка:** CI запускает тесты, миграции, линтер и проверку зависимостей; сценарии повторной оплаты, повторного возврата и поддельного webhook воспроизводятся и проходят.

### 7.2. Прогнать тестовый магазин ЮKassa

Выполнить создание и успешную оплату, отмену/неуспех, полный возврат, повторные webhook, потерю ответа, отключение webhook и сверку. Проверить данные чека, если фискализация обязательна для выбранного магазина. Частичный возврат проверить после добавления этой функции.

**Приёмка:** есть журнал тестов с локальным ID, ID ЮKassa и ожидаемым/фактическим итогом; все расхождения исправлены; в тестовой БД не осталось необъяснённых `unknown`.

### 7.3. Выполнить проверку допуска в production

После выбора допустимого статуса продавца с владельцем бизнеса и ответственным за безопасность подтвердить договор и настройки настоящего магазина ЮKassa, фискализацию/чеки для выбранного статуса, политику данных, права доступа, мониторинг, резервные копии, инструкцию инцидента и способ остановить новые платежи. Настроить webhook в настоящем кабинете и провести одну контролируемую реальную оплату и возврат.

**Приёмка:** подписанный чек-лист допуска, подтверждённая тестовая реальная операция и возврат, запись в БД и кабинете ЮKassa совпадают; ответственные знают, как отключить приём новых платежей и разобрать зависшую операцию.

## 8. Обязательный этап после MVP: автосписания

[Отдельный план этапа 8](.docs/8.PLAN.md).

### 8.1. Согласовать правила подписки и согласие пользователя

Определить период, сумму и дату следующего списания, способ уведомления, отмены и изменения тарифа. Зафиксировать явное согласие пользователя на повторные списания и способ его отзыва; проверить требования ЮKassa и применимые требования к оферте и чекам до включения функции.

**Приёмка:** опубликованы правила подписки и сценарии согласия/отмены; в БД сохраняются время, версия условий и факт согласия; после отзыва согласия новые списания не планируются.

### 8.2. Сохранить способ оплаты для повторных списаний

При первом платеже запросить у ЮKassa сохранение способа оплаты по поддерживаемому сценарию. Хранить только идентификатор способа оплаты и связь с пользователем; реквизиты карты не хранить. Учитывать отказ в сохранении способа.

**Приёмка:** тестовый платёж с согласием даёт пригодный для повторного списания способ оплаты; без согласия способ не сохраняется; отказ не активирует автосписания.

### 8.3. Реализовать расписание и повторный платёж

Планировщик выбирает наступившие периоды. Для каждого периода создавать уникальную локальную операцию и устойчивый ключ идемпотентности; не начинать второй платёж за тот же период при параллельном запуске, рестарте или таймауте. Результат подтверждать через API ЮKassa и сверку, как в MVP.

**Приёмка:** два параллельных планировщика создают не более одного платежа за период; перезапуск и потерянный ответ не приводят к повторному списанию; подтверждённый платёж продлевает доступ ровно на один период.

### 8.4. Обработать отказ, отмену и восстановление

Задать ограниченный график повторных попыток, уведомление пользователя о неудаче, срок действия подписки при отказе и смену способа оплаты. Отмена подписки должна останавливать будущие списания, не меняя уже оплаченный срок; ручной возврат обрабатывается отдельно.

**Приёмка:** тестовые отказ, истёкший способ оплаты и отмена дают ожидаемые статусы и уведомления; после отмены планировщик не создаёт новых платежей; инструкция оператору покрывает спорное списание.

### 8.5. Проверить тестовый и реальный цикл

Прогнать первый платёж, следующее списание, отказ, повтор, отмену и возврат в тестовой среде; перед включением в production провести контролируемый реальный цикл и сверить его с кабинетом ЮKassa.

**Приёмка:** результаты всех сценариев задокументированы; нет двойных списаний или продлений; включение автосписаний управляется отдельным флагом и не затрагивает пользователей без согласия.

## 9. После MVP: смена плана в оплаченный период и частичный возврат

[Отдельный план этапа 9](.docs/9.PLAN.md).

### 9.1. Зафиксировать правила изменения плана

Выбрать правило доплаты или кредита за неиспользованную часть, дату вступления нового плана в силу и поведение при неуспешной доплате. Изменение оформлять отдельным заказом/операцией, сохраняя историю исходного оплаченного периода.

**Приёмка:** для всех сочетаний месячного/годового периода и планов описаны сумма и дата изменения; тест показывает, что отказ доплаты сохраняет исходный доступ, а повтор запроса не меняет план дважды.

### 9.2. Добавить частичный возврат

Расширить административный API суммой возврата. Под блокировкой учитывать завершённые и ожидающие возвраты, ограничения способа оплаты ЮKassa и правило изменения оставшегося доступа. Каждая попытка остаётся отдельной идемпотентной записью с точной суммой.

**Приёмка:** сумма всех возвратов не превышает платёж при параллельных запросах; неподдерживаемый способ оплаты отклоняется; история возвратов и остаток видны оператору; доступ после возврата соответствует принятому правилу.
