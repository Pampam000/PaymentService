# Шаг 1.1 — участники и владение данными

Отдельный сервис на Litestar для приёма оплаты подписки на конструктор через ЮKassa. Связанные документы: [план](../PLAN.md), [API шага 1.2](1.2-API_CONTRACT.md), [жизненный цикл шага 1.3](1.3-LIFECYCLE.md). Работающий API ещё не создан.

## Шаг 1.1. Участники и владение данными

| Участник | Ответственность |
| --- | --- |
| Пользователь | Выбирает тариф/период в интерфейсе, переходит на страницу ЮKassa и оплачивает. Не задаёт итоговую сумму или статус. |
| BotConstructorBackend | Владеет тарифами, ценами, заказом на период подписки и правом доступа к конструктору. Создаёт неизменяемый снимок заказа: `order_id`, `user_id`, тариф/период, сумма в копейках, валюта `RUB`. Инициирует платёж от имени пользователя через защищённый внутренний вызов. |
| AuthService | Владеет учётной записью пользователя; её UUID используется как `user_id`. Не определяет цену и не проводит платёж. |
| PaymentService | Владеет локальными записями платежей и возвратов, ключами идемпотентности, связью с `order_id` и ID ЮKassa. Проверяет сумму заказа у доверенного Backend, вызывает ЮKassa, подтверждает итоговый статус и сообщает его Backend. Не продлевает подписку напрямую. |
| ЮKassa | Проводит оплату, хранит платёжные реквизиты и сообщает состояние операций. Её объект, полученный через API, служит внешним подтверждением результата. |
| Владелец сервиса / уполномоченный администратор | Разрешает возврат через защищённый административный API. Конечный пользователь не может инициировать возврат напрямую. |

```text
Пользователь → Backend: выбрать подписку
Backend → своя БД: создать заказ и зафиксировать цену
Backend → PaymentService: создать платёж по order_id
PaymentService → Backend: проверить заказ и его сумму по доверенному каналу
PaymentService → ЮKassa: создать платёж
PaymentService → Backend → Пользователь: вернуть ссылку на страницу оплаты
ЮKassa → PaymentService: webhook
PaymentService → ЮKassa: проверить актуальный статус и реквизиты операции
PaymentService → Backend: доставить подтверждённый результат
Backend → своя БД: выдать/продлить подписку ровно один раз для заказа
```

Правило денег: сумма и валюта берутся только из сохранённого заказа Backend. PaymentService сверяет переданную сумму с заказом или получает её из доверенного внутреннего API Backend. Поля от браузера, Telegram-бота и webhook не могут изменить цену. Возврат на сайт и наличие ссылки на оплату не подтверждают поступление денег. Подписка активируется только после подтверждённого `succeeded`; Backend должен игнорировать повтор того же результата.

«Возврат только через администратора» относится к отдельной операции возврата **успешно списанного** платежа. Если оплата отклонена или отменена (`canceled`), возврат через наш API не создаётся и участие администратора не требуется. При неясном результате (`status=pending`, `resolution_status=unknown`) сервис сначала сверяет платёж с ЮKassa, чтобы не принять списание за отказ.

MVP продаёт календарный месяц или год выбранного плана разовым платежом. Backend фиксирует в каждом заказе план, тип периода и цену на момент покупки. Оплаченный период сохраняется отдельной записью с конкретными датами начала и окончания, а не только общей датой окончания подписки: это позволит позже добавить смену плана и разбор возврата конкретной оплаты. Смена плана посреди оплаченного периода в MVP недоступна.

Покупка следующего периода заранее разрешена. Backend ставит его после конца текущего оплаченного периода; если активного периода нет, он начинается после подтверждения оплаты. Один заказ создаёт не более одного оплаченного периода. Если следующий период относится к другому плану, новый план вступает в силу только после окончания текущего периода.

Для всех тарифов используется только календарная длительность. Правило расчёта даты окончания для 29–31 числа, 29 февраля и последовательных продлений закреплено в [шаге 1.3](1.3-LIFECYCLE.md). Уже оплаченные периоды не пересчитываются при изменении настроек тарифа.

В MVP администратор может оформить только полный возврат успешного платежа. PaymentService с первого дня хранит каждый возврат отдельной операцией с точной суммой и связью с исходным платежом. Это позволяет позже добавить частичные возвраты, проверку остатка и правила изменения доступа без замены модели платежей. Правило доступа после полного возврата закреплено в [шаге 1.3](1.3-LIFECYCLE.md).

Автосписания обязательны после MVP; их согласие, сохранение способа оплаты, расписание, отмена и обработка отказов выделены в [этап 8 плана](../PLAN.md). До завершения этого этапа повторных списаний без участия пользователя нет.

## Что требуется уточнить в следующих шагах

- В Backend сейчас нет модели заказа, тарифа или подписки. Их формат, хранение и способ проверки заказа определяются до реализации API (шаг 1.2).
- Сейчас у владельца проекта нет ИП. Разработку и тестовый магазин ЮKassa можно использовать до выбора статуса продавца; реальные платежи требуют отдельного допуска по шагу 7.3 [плана](../PLAN.md).
- Способ аутентификации внутренних вызовов и административных возвратов определяется в шагах 1.2 и 3.1.
- Правила будущих автосписаний и согласия пользователя определяются перед этапом 8; MVP не должен выдавать разовую оплату за подключённое автопродление.

## Проверка шага 1.1

- [x] Известно, что оплачивается: период подписки на конструктор.
- [x] Источник цены: зафиксированный заказ в Backend, а не клиентский запрос.
- [x] Создание платежа: Backend через внутренний вызов PaymentService.
- [x] Возврат: только уполномоченный администратор через защищённый API.
- [x] Подтверждение оплаты: PaymentService проверяет ЮKassa и доставляет результат Backend; подписку выдаёт Backend один раз.
