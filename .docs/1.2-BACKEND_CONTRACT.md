# Внутренний контракт с BotConstructorBackend (шаг 1.2)

Этот документ описывает маршруты, которые нужно добавить в Backend. Они ещё не реализованы. Все вызовы идут по HTTPS во внутренней сети. Браузер и Telegram-бот не обращаются к ним напрямую. Продуктовые правила — в [шаге 1.1](1.1-SCOPE.md), маршруты PaymentService — в [OpenAPI](1.2-openapi.yaml).

## Проверка заказа перед созданием платежа

`GET /internal/billing/orders/{order_id}` вызывается PaymentService с отдельным служебным bearer-токеном. Backend возвращает только уже сохранённый и неизменяемый заказ. Пример `200`:

```json
{
  "order_id": "1fd35547-a8cf-4660-8231-93bed49b4c4a",
  "user_id": "f3562d82-b84f-4512-9997-eb24ef2f8a8d",
  "plan_id": "basic",
  "period": "month",
  "amount_kopecks": 99000,
  "currency": "RUB",
  "status": "awaiting_payment"
}
```

Допустимые `period`: `month`, `year`; оба календарные. `status=awaiting_payment` допускает создание платежа. Другие состояния отклоняются; сумма и план не меняются после создания заказа. PaymentService сохраняет снимок ответа и сверяет заказ перед вызовом ЮKassa. Если Backend недоступен, платёж не создаётся, запрос получает `503`. Ошибки: `401/403` — служебный доступ; `404` — заказа нет; `409` — заказ уже оплачен или закрыт. Общий формат ошибки такой же, как в [1.2-openapi.yaml](1.2-openapi.yaml). Пример `404`:

```json
{"code":"order_not_found","message":"Заказ не найден","request_id":"9c76e86b-965f-47c9-9654-e9998aa87e16"}
```

## Подтверждённый результат операции

`POST /internal/billing/payment-events` вызывается PaymentService с **другим** служебным bearer-токеном после проверки объекта через API ЮKassa. Пример запроса:

```json
{
  "event_id": "c272c06e-9ea3-41a4-8c18-98ae105d6f5d",
  "payment_id": "cb9e27cf-542c-44f4-87fa-3b92fd704b03",
  "order_id": "1fd35547-a8cf-4660-8231-93bed49b4c4a",
  "status": "succeeded",
  "amount_kopecks": 99000,
  "currency": "RUB"
}
```

Допустимые статусы события платежа: `succeeded`, `canceled`; для подтверждённого возврата отдельное событие `refund.succeeded` с `refund_id`, суммой и ссылкой на платёж. Точную схему возврата закрепить вместе с правилом изменения доступа в шаге 1.3. Backend сверяет `order_id`, сумму и валюту со своим заказом, сохраняет `event_id` под уникальным ограничением и применяет результат в одной транзакции. Повтор того же события возвращает `200` и не выдаёт подписку второй раз. Пример ответа `200`:

```json
{"status":"accepted"}
```

Ошибки: `401/403` — служебный доступ, `400` — неверное тело, `409` — несовпадение с заказом, `503` — временная ошибка. Пример `409`:

```json
{"code":"order_mismatch","message":"Сумма события не совпадает с заказом","request_id":"9c76e86b-965f-47c9-9654-e9998aa87e16"}
```

PaymentService сохраняет исходящее событие в своей БД в той же транзакции, что и подтверждённый статус, и повторяет доставку до `200`. При `409` событие отправляется на разбор оператору; оно не удаляется. Backend может дополнительно запрашивать `GET /payments/{id}` для восстановления. Конечный пользователь не получает право вызвать этот endpoint.

## Административный возврат и токены

Администратор проходит обычную пользовательскую аутентификацию Backend; Backend проверяет его роль и вызывает `POST /payments/{id}/refunds` с отдельным `AdminToken`. PaymentService не принимает пользовательский JWT как доказательство роли администратора. `BackendToken`, `AdminToken`, токен проверки заказов и токен событий — разные секреты с минимальными правами; хранить их во внешнем хранилище секретов, поддержать ротацию и не печатать в логах. Точные переменные окружения и механизм ротации — шаг 3.1.
