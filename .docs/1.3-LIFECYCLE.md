# Шаг 1.3 — состояния, календарные периоды и возвраты

Правила продукта: [шаг 1.1](1.1-SCOPE.md). Формат публичного для Backend API: [OpenAPI](1.2-openapi.yaml). Взаимодействие с Backend: [внутренний контракт](1.2-BACKEND_CONTRACT.md). Этот документ фиксирует согласованные правила; код ещё не реализован.

## Платёж и выяснение результата

`status` — локальное подтверждённое состояние платежа: `pending`, `succeeded`, `canceled`. `resolution_status` — отдельно `known` или `unknown`. В частности, `pending + unknown` означает, что запрос к ЮKassa мог выполниться, но ответ потерян либо итог нельзя подтвердить. Это не утверждение, что ЮKassa считает платёж `pending`. Подписка при этой паре не выдаётся, новый платёж с новым ключом не создаётся. Сервис повторяет запрос с прежним ключом в допустимом окне и/или сверяет операцию через API ЮKassa; после истечения окна без достоверного результата требуется разбор оператором. Для возврата действует та же пара полей.

| Текущее `status` | Подтверждение через API ЮKassa | Новое `status` | Действие |
| --- | --- | --- | --- |
| `pending` | Объект ещё `pending` | `pending` | Продолжать ожидание и сверку. |
| `pending` | `succeeded` | `succeeded` | Создать устойчивое событие для Backend. |
| `pending` | `canceled` | `canceled` | Не выдавать подписку; сообщить Backend об отказе. |
| `succeeded` или `canceled` | Повторное/запоздалое уведомление | Без изменения | Не повторять выдачу доступа и возврат. |

`resolution_status` становится `unknown` при неясном ответе на создание/возврат и возвращается в `known` только после достоверной проверки. `confirmation_url`, возврат браузера на сайт и тело webhook сами по себе не подтверждают успех. `succeeded` и `canceled` считаются конечными статусами платежа; возврат хранится отдельной операцией и не меняет платёж `succeeded` обратно в `canceled`.

## Календарные периоды подписки

- Все времена хранятся как UTC instant; интервалы доступа полуоткрытые `[starts_at, ends_at)`. В `ends_at` доступ уже закончился.
- Месяц и год — календарные, не 30/365 суток. Базовое число дня месяца (и время суток) берётся при первом начале непрерывной цепочки подписки. При продлении эта исходная календарная «годовщина» сохраняется, даже если промежуточная дата была сдвинута на последний день короткого месяца.
- Если целевой месяц не содержит исходного числа, граница ставится на последний день этого месяца. Для годового периода 29 февраля в невисокосный год становится 28 февраля; при следующем високосном году снова 29 февраля.
- Примеры для начала в 12:00 UTC: `31.01.2027 → 28.02.2027 → 31.03.2027`; `29.02.2024 → 28.02.2025 → 28.02.2026 → 28.02.2027 → 29.02.2028` для годовых продлений.
- При покупке заранее оплаченный период ставится после текущего оплаченного периода. Если новый план отличается, он вступает в силу только в начале нового периода. Если непрерывная цепочка прервалась, следующая покупка начинает новую цепочку и новую дату «годовщины».
- Backend хранит каждый оплаченный период отдельно: `order_id`, план, тип периода, `starts_at`, `ends_at`, исходное число/время цепочки и состояние доступа. Дату окончания предыдущего периода не перезаписывать. Один подтверждённый заказ создаёт не более одного периода даже при повторе события.

## Полный возврат

Только администратор может запросить полный возврат платежа со статусом `succeeded`. Возврат имеет собственные `status`, `resolution_status`, ID, сумму в копейках, ключ идемпотентности и ссылку на платёж. До подтверждения `refund.succeeded` оплаченный период не удаляется; `pending + unknown` возврата требует сверки.

После подтверждённого полного возврата Backend помечает **период, купленный этим платежом**, как возвращённый. Если он активен сейчас, доступ по нему прекращается немедленно; если он ещё впереди, он не активируется. Другие оплаченные периоды сохраняют прежние даты и не сдвигаются. Для уже истёкшего периода фиксируется возврат в истории без изменения прошлого доступа. Текущий доступ вычисляется по действующим невозвращённым периодам; наличие будущего оплаченного периода не даёт доступа раньше его `starts_at`.

Пока возврат `pending` или его результат `unknown`, доступ не изменяется автоматически. Оператор видит состояние возврата и может инициировать разбор; повторный запрос с новым ключом не должен создавать второй возврат на ту же сумму.

## Условие перед настоящими платежами

Сейчас у владельца проекта нет ИП. Это не блокирует проектирование, разработку и проверку в тестовом магазине ЮKassa: тестовые платежи не списывают настоящие деньги. До подключения настоящего магазина нужно выбрать допустимый статус продавца (например, ИП или самозанятый, если деятельность допускает этот режим), заключить договор и определить подходящие для выбранного статуса правила чеков. Их нельзя корректно закрепить заранее без решения о статусе продавца. Production-допуск остаётся отдельным шагом 7.3 [плана](../PLAN.md).
