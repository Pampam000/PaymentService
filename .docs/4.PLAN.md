# 4. Безопасно обрабатывать уведомления

## 4.1. Принять webhook

Настроить HTTPS endpoint и подписку в кабинете ЮKassa на `payment.succeeded`, `payment.canceled`, `refund.succeeded` и другие события, реально нужные выбранному сценарию. Ограничить размер тела, проверить формат и не доверять переданному статусу.

**Приёмка:** корректный webhook принят; битый/слишком большой запрос отклонён; URL доступен ЮKassa по HTTPS с допустимым TLS.

## 4.2. Подтвердить событие у ЮKassa

По ID из webhook запросить объект через API ЮKassa и сверить его ID, сумму, валюту, принадлежность локальной операции и актуальный статус. Для возврата сверить ID возврата, ID платежа и сумму. Не полагаться только на IP или тело webhook; при недоступности ЮKassa оставить событие для повторной проверки и не переводить платёж в успех.

**Приёмка:** поддельный `payment.succeeded`, чужой ID и неверная сумма не меняют статус; настоящий webhook после запроса API меняет статус; временная ошибка API приводит к повторной обработке или последующей сверке.

## 4.3. Сделать обработку повторов и конкуренции безопасной

Менять состояние в транзакции с блокировкой строки/условным обновлением. Повторное или запоздавшее событие не должно откатывать конечный статус и повторно запускать выдачу товара. Результат для Backend публиковать через устойчивое событие/outbox или другой документированный механизм с повторной доставкой.

**Приёмка:** 10 одинаковых и одновременно пришедших webhook дают одно изменение состояния и одно бизнес-событие; после сбоя между записью статуса и уведомлением Backend событие доставляется повторно; Backend также обрабатывает повтор без второй выдачи.
