# Шаг 1.2 — пояснения к контракту API

Статус: контракт шага 1.2 описан, реализация ещё отсутствует. Источники точного формата: [OpenAPI PaymentService](1.2-openapi.yaml) и [внутренние маршруты Backend](1.2-BACKEND_CONTRACT.md). Продуктовые правила: [шаг 1.1](1.1-SCOPE.md). Сервер будет на Litestar. Все внутренние маршруты доступны только Backend или уполномоченному администратору; браузер обращается к Backend.

Маршрут возврата предназначен только для успешного (`succeeded`) платежа. Неуспешный или отменённый платёж не требует запроса возврата от администратора.

## Внутренний контракт Backend ↔ PaymentService

| Метод и путь | Кто вызывает | Вход | Успешный ответ |
| --- | --- | --- | --- |
| `POST /payments` | Backend | `Idempotency-Key`, JSON `{ "order_id": "..." }` | `201`, `{ "id": "...", "order_id": "...", "status": "pending", "confirmation_url": "https://..." }` |
| `GET /payments/{id}` | Backend | ID локального платежа | `200`, `{ "id": "...", "order_id": "...", "status": "pending", "amount_kopecks": 10000, "currency": "RUB" }` |
| `POST /payments/{id}/refunds` | Администратор через Backend | `Idempotency-Key`, JSON `{ "reason": "..." }` | `201`, `{ "id": "...", "payment_id": "...", "status": "pending", "amount_kopecks": 10000 }` |
| `GET /refunds/{id}` | Администратор через Backend | ID локального возврата | `200`, `{ "id": "...", "payment_id": "...", "status": "pending", "amount_kopecks": 10000 }` |
| `POST /webhooks/yookassa` | ЮKassa | Уведомление провайдера | `200` после принятия к проверке; тело не считается достоверным до запроса объекта через API ЮKassa |
| `GET /health/live` | Оркестратор | — | `200`, если процесс работает |
| `GET /health/ready` | Оркестратор | — | `200`, если сервис готов и БД доступна; `503` иначе |

PaymentService получает сумму, валюту, `user_id` и оплачиваемый период из **неизменяемого заказа Backend** через защищённый внутренний запрос по `order_id`. Клиент не передаёт сумму в `POST /payments`. Формат ответа Backend для проверки заказа нужно определить вместе с моделью заказа. Нужны как минимум `order_id`, `user_id` (UUID AuthService), `amount_kopecks`, `currency=RUB`, ID тарифа, `period=month|year` и состояние заказа. Оба периода календарные. При повторе того же ключа и тела возвращается прежняя операция; тот же ключ с другим телом даёт `409`.

MVP поддерживает разные планы с календарным периодом месяц или год. Backend фиксирует план, период и цену в заказе, а после оплаты создаёт отдельную запись оплаченного периода с датами начала и окончания. При покупке заранее новый период начинается после конца действующего; новый план начинает действовать только в начале своего периода. Посреди действующего периода смены плана нет. Периоды не следует хранить только как одно изменяемое поле `expires_at`, иначе будущая смена плана и возврат конкретной оплаты потребуют переделки данных. Правило для 29–31 числа, 29 февраля и цепочки продлений определяется в шаге 1.3.

В MVP `POST /payments/{id}/refunds` оформляет **полный** возврат: сумма берётся из исходного платежа, клиент её не задаёт. В таблице возвратов сохраняется сумма операции, а не только флаг `refunded`; это обеспечивает будущий учёт частичных возвратов. Добавление частичной суммы в API позже потребует отдельного правила расчёта остатка и доступа, но не замены таблицы платежей и возвратов.

## Доставка результата в Backend

Предложение: PaymentService отправляет во внутренний endpoint Backend событие `{ "event_id": "...", "payment_id": "...", "order_id": "...", "status": "succeeded" }`. Доставка повторяется до подтверждения. Backend применяет `event_id`/`order_id` идемпотентно и выдаёт период подписки только после подтверждённого `succeeded`. Это внутреннее событие, не webhook ЮKassa. Конкретный маршрут и способ аутентификации согласуются при реализации обеих сторон.

## Ошибки и доступ

Общий формат ошибки: `{ "code": "...", "message": "...", "request_id": "..." }`; без секретов и исходного ответа ЮKassa. `400` — неверный формат; `401/403` — нет доступа; `404` — операция/заказ не найдены или недоступны вызывающему; `409` — конфликт ключа или состояния; `422` — валидный формат, но недопустимая сумма/операция; `503` — временно недоступны Backend/ЮKassa/БД до создания локальной операции. При неясном результате у провайдера локальная операция остаётся `status=pending`, `resolution_status=unknown`, возвращается `202` и запускается сверка. Успешный или отменённый платёж не выводится из ответа с `unknown`.

## Открытые решения

Даты и поведение подписки после возврата зафиксированы в [шаге 1.3](1.3-LIFECYCLE.md).

Контракт оформлен как OpenAPI 3.1 с примерами успешного и ошибочного ответа. При реализации Litestar его генерируемую OpenAPI-схему нужно сверить с [файлом контракта](1.2-openapi.yaml); расхождения исправить до подключения Backend.
