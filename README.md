## Локальный запуск (шаг 2.1)

Требуется Python 3.14. Из каталога `PaymentService` установите закреплённые зависимости:

```bash
python3.14 -m venv .venv
.venv/bin/python -m pip install -e .
```

Если `.env` ещё нет, создайте его из `.env.example` и укажите отдельного пользователя, пароль и базу PaymentService. При использовании PostgreSQL из `BotConstructorBackend/docker-compose.yml` адрес хоста — `127.0.0.1:5433`, имя базы — `payment_service`. Файл `.env` не хранится в Git.

```bash
test -f .env || cp .env.example .env
```

После заполнения `.env` запустите сервис:

```bash
.venv/bin/python -m uvicorn payment_service.main:app --host 127.0.0.1 --port 8002
```

`GET /health/live` отвечает `200`, пока приложение работает. `GET /health/ready` отвечает `200` только если PostgreSQL доступен; при отсутствии или недоступности БД отвечает `503`. Оба маршрута подходят для проб Docker/Kubernetes. В production установите `APP_ENV=production` и `DATABASE_URL`: отсутствие адреса БД остановит запуск. Переменные окружения имеют приоритет над `.env`.

## Хранилище и миграции (шаг 2.2)

Для новой установки создайте в PostgreSQL отдельную роль `payment_service` с собственным паролем и пустую базу `payment_service`, принадлежащую этой роли. Запишите пароль только в локальный `.env`. Из каталога `PaymentService` выполните:

```bash
.venv/bin/python -m payment_service.migrate upgrade
.venv/bin/python -m payment_service.migrate current
```

Повторный `upgrade` должен оставить схему без изменений. Миграция создаёт `payments` и `refunds`; сумма каждой операции хранится целым числом копеек. Уникальные ограничения защищают `order_id`, ключ идемпотентности и ID ЮKassa в пределах соответствующей таблицы. Записи оплаченных периодов остаются в базе Backend согласно [контракту](.docs/1.2-BACKEND_CONTRACT.md).

## Настройки магазина (шаг 2.3)

`YOO_MODE=test` выбирает только `YOO_TEST_SHOP_ID` и `YOO_TEST_SECRET_KEY`; `YOO_MODE=live` выбирает только `YOO_LIVE_SHOP_ID` и `YOO_LIVE_SECRET_KEY`. Режим `live` разрешён лишь при `APP_ENV=production`. Для production нужны адрес БД, оба параметра выбранного магазина и `PAYMENT_RETURN_URL`; рабочий `return_url` должен использовать HTTPS. При совпадении тестового и рабочего магазина или ключа запуск прерывается. Пароли и ключи задавайте в окружении или локальном `.env`, не в репозитории и не в логах.

`PAYMENT_RETURN_URL` задаётся оператором сервиса. Клиентский `POST /payments` принимает только `order_id`; произвольный `return_url` в нём запрещён [контрактом](.docs/1.2-openapi.yaml). При подключении ЮKassa адаптер должен брать URL и выбранные реквизиты из `Settings`, а не из запроса. URL возврата пользователя не подтверждает оплату.

В `.env.example` указаны пустые поля магазина и фиктивный пароль БД. Для GitHub CI добавлена проверка секретов Gitleaks; локальный `.env` исключён из Git.

## Служебный доступ (шаг 3.1)

`BACKEND_TOKEN` разрешает создание и чтение платежей, `ADMIN_TOKEN` — создание и чтение возвратов. Токены различаются; в production оба обязательны. Backend передаёт нужный секрет в заголовке `Authorization: Bearer <token>`. Пользовательский JWT и токен другого назначения не подходят. Backend проверяет роль администратора до вызова маршрута возврата. Webhook и маршруты здоровья не требуют этих токенов.

Храните токены в менеджере секретов или переменных окружения, доступных только сервисам. Для ротации согласованно обновите секрет в PaymentService и Backend и перезапустите оба сервиса. Текущая реализация принимает один токен каждого назначения, поэтому переключение требует краткого окна обслуживания; при подозрении на компрометацию сначала закройте доступ к внутреннему API, затем замените секреты. Не записывайте токены в логи и Git.

## Проверка заказа (шаг 3.2)

`BACKEND_BASE_URL` задаёт адрес доверенного Backend, `ORDER_LOOKUP_TOKEN` — отдельный токен для чтения заказа через `GET /internal/billing/orders/{order_id}`. В production нужен HTTPS. Ответ Backend проверяется по ID заказа, UUID пользователя, плану, календарному периоду, целой положительной сумме в копейках и валюте `RUB`. При создании платежа эти данные сохраняются как снимок заказа.

## Локальное создание платежа (шаг 3.3)

`POST /payments` требует служебный `BACKEND_TOKEN`, заголовок `Idempotency-Key` длиной 1–64 символа и тело только с `order_id`. Сервис сначала ищет сохранённый ключ, затем проверяет заказ у Backend и атомарно создаёт платёж вместе со снимком заказа. Повтор с тем же ключом и заказом возвращает ту же операцию (`200`), новый ключ для уже занятого заказа или тот же ключ для другого заказа — `409`.

## Адаптер ЮKassa (шаг 3.4)

После сохранения локального платежа сервис однократно помечает попытку обращения к ЮKassa в БД и отправляет запрос с устойчивым ключом, равным локальному ID платежа. Адаптер использует API ЮKassa v3, выбранные реквизиты магазина и `PAYMENT_RETURN_URL` из настроек. Сумма переводится из целых копеек в строку с двумя десятичными знаками. При достоверном ответе сохраняются ID ЮKassa и ссылка подтверждения, локальный статус остаётся `pending`. При потере ответа операция остаётся `pending + unknown`, повтор `POST /payments` не отправляет второй запрос ЮKassa и возвращает `202`. Сверка и разрешение таких операций — шаг 3.5.

Для другого провайдера добавьте модуль в `payment_service/adapters` с интерфейсом `PaymentAdapter`, используйте общие `ProviderPaymentCreate` и `ProviderPaymentResult`, затем зарегистрируйте модуль в `get_adapter()` и разрешите его имя в `PAYMENT_PROVIDER`. Сервис создания платежей работает только с этими общими схемами; формат запроса и ответа конкретного провайдера остаётся внутри адаптера.


## Сверка неопределённых платежей (шаг 3.5)

После миграции `0004_reconciliation` оператор выводит зависшие операции командой
`.venv/bin/python -m payment_service.reconcile` и сверяет конкретную операцию
командой `.venv/bin/python -m payment_service.reconcile "$payment_id"`.
Команду можно запускать периодически: попытки атомарно ограничены пятью вызовами
с интервалом не менее минуты. Если ID ЮKassa уже известен, сервис запрашивает
платёж по нему. Если ID неизвестен, создание повторяется только с исходным ключом
и только в течение 24 часов с первой попытки. Результат `manual_review` требует
ручной проверки в кабинете ЮKassa; новый платёж с другим ключом создавать нельзя.

## Чтение статуса платежа (шаг 3.6)

Backend вызывает `GET /payments/{id}` с `Authorization: Bearer <BACKEND_TOKEN>`, где
`id` — локальный UUID платежа из ответа `POST /payments`. Сервис возвращает `200`
и сохранённые `id`, `order_id`, `status`, `resolution_status`, `amount_kopecks`,
`currency`, `confirmation_url`. Отсутствующий ID даёт `404`, недоступная БД — `503`.
Чтение не обращается к ЮKassa; до подтверждённого изменения статуса ответ остаётся
`pending`. Сверка с ЮKassa запускается отдельно командой выше.

## Приём уведомлений ЮKassa (шаг 4.1)

`POST /webhooks/yookassa` доступен без служебного токена. Он принимает только JSON-уведомления `payment.succeeded`, `payment.canceled` и `refund.succeeded` с непустым `object.id`; тело ограничено 64 КиБ. Неверный формат получает `400`, превышение размера — `413`. Сервис ищет локальную операцию по ID ЮKassa, запрашивает объект через API провайдера и сверяет ID, сумму, валюту и связь с исходным платежом. Подтверждённый конечный статус сохраняется; при временной ошибке API, ещё не подтверждённом статусе или неизвестном локально ID ответ `503` просит повторить доставку. Несовпадающий объект не меняет локальный статус.

Для внешнего доступа разместите сервис за HTTPS reverse proxy с действующим сертификатом TLS и направьте `/webhooks/yookassa` на приложение. Настройте этот публичный URL в кабинете ЮKassa и подпишитесь на три указанных события; проверьте доступность URL извне и доставку тестового уведомления. Устойчивую доставку результата в Backend добавляет шаг 4.3.

## Повторы уведомлений и доставка результата (шаг 4.3)

Примените миграцию `0005_outbox` командой `.venv/bin/python -m payment_service.migrate upgrade`. Первый подтверждённый конечный статус платежа и событие для Backend записываются одной транзакцией. Повторный webhook не создаёт второе событие и не меняет конечный статус. Для успешного возврата создаётся отдельное событие `refund.succeeded`.

Задайте `PAYMENT_EVENT_TOKEN`, отличный от остальных служебных токенов. Запускайте `.venv/bin/python -m payment_service.deliver_events` периодически, например раз в минуту. Команда отправляет события на `POST {BACKEND_BASE_URL}/internal/billing/payment-events` и повторяет отправку с тем же `event_id` до ответа `200`; при `409` помечает событие для ручного разбора. Их ID выводит `.venv/bin/python -m payment_service.deliver_events --review`. Backend должен сохранять `event_id` с уникальным ограничением и применять результат к заказу в той же транзакции; повтор того же `event_id` должен возвращать `200` без второй выдачи периода. До реализации этого маршрута в Backend события остаются в outbox.

## Резервирование полного возврата (шаг 5.1)

`POST /payments/{id}/refunds` принимает `ADMIN_TOKEN`, `Idempotency-Key` и JSON с необязательным `reason`. Сумма берётся из подтверждённого платежа. Запрос сохраняет локальный возврат `pending` и резервирует всю сумму; повтор с тем же ключом возвращает ту же запись. Другой ключ для уже зарезервированного платежа получает `409`.

## Создание возврата (шаг 5.2)

Примените миграцию `0006_refund_reconciliation` командой `.venv/bin/python -m payment_service.migrate upgrade`. После локального резервирования сервис отправляет возврат в ЮKassa с ключом идемпотентности, равным локальному ID возврата. `GET /refunds/{id}` с `ADMIN_TOKEN` возвращает сохранённые статус, сумму и ID. Потерянный ответ оставляет `pending + unknown`; повтор `POST` не создаёт вторую операцию. Если ID ЮKassa неизвестен, повторное создание допускается только с прежним ключом в течение 24 часов; позже требуется ручная проверка.

## Подтверждение возврата (шаг 5.3)

Запускайте `.venv/bin/python -m payment_service.reconcile_refunds` периодически и сверяйте выведенные ID той же командой с аргументом. Список включает все `pending` возвраты, в том числе с известным ID ЮKassa. Сверка запрашивает объект ЮKassa; окончательные `succeeded` и `canceled` фиксируются только после проверки суммы и исходного платежа. Подтверждённый `canceled` освобождает зарезервированную сумму, а `succeeded` создаёт одно событие для Backend. Уведомление `refund.succeeded` также проверяется через API ЮKassa перед изменением статуса. Период подписки меняет Backend после доставки события.

## Плановая сверка (шаг 6.1)

Запускайте `.venv/bin/python -m payment_service.reconcile --run` и
`.venv/bin/python -m payment_service.reconcile_refunds --run` отдельно по расписанию, например
каждые пять минут. Команды проверяют все незавершённые операции и завершённые за
последние семь дней. Результат каждой проверки выводится вместе с локальным ID;
сохраняйте вывод планировщика для разбора. `manual_review` означает несовпадение
ID, суммы, связи с платежом или конечного статуса либо истечение окна повторного
создания. Не меняйте локальный статус без проверки в ЮKassa. `unknown` означает
недоступность API; повторите запуск позже. После пропущенного webhook сверка
запишет подтверждённый статус и событие для Backend.

## Логи и метрики (шаг 6.2)

Примените миграцию `0007_observability`. Операции пишутся в журнал
`payment_service.operations` (имя журнала, не запускаемый модуль) в JSON с полями `correlation_id`, `local_id`,
`provider_id`, `operation`, `outcome`, `error_class`. Секреты, реквизиты и тело
webhook в этот журнал не передаются. Для ошибок HTTP `request_id` в ответе
совпадает с `correlation_id` журнальной записи. Сохраняйте stdout приложения и
плановых команд в защищённом централизованном журнале.

`GET /internal/metrics` с `Authorization: Bearer <ADMIN_TOKEN>` отдаёт текстовые
метрики: максимальный возраст `pending`/`unknown`, отставание сверки по времени
последней попытки, число нерешённых расхождений, ошибки доставки и сверки,
ошибки API и события outbox для ручного разбора. Счётчики работников и
расхождения хранятся в PostgreSQL; счётчики ошибок API относятся к процессу
приложения. Оповещайте оператора при росте ошибок доставки, появлении
расхождений или outbox review, а также при `pending` старше 15 минут,
`unknown` старше 5 минут и отставании сверки больше 10 минут.

Сейчас используется собственный endpoint метрик: система мониторинга ещё не
подключена, а показатели состояния операций вычисляются по PostgreSQL. Его
текстовый формат можно собирать Prometheus после настройки защищённого доступа.
Ограничение текущей реализации: счётчики ошибок API хранятся в памяти процесса,
сбрасываются при перезапуске и различаются между несколькими процессами;
счётчики работников в БД требуют отдельной миграции и поддержки. Перед
production-развёртыванием стоит заменить самодельные счётчики стандартным
клиентом Prometheus, оставив запросы к БД для показателей состояния операций.

## Резервное копирование и восстановление (шаг 6.3)

Для локальной проверки в Docker запустите из каталога PaymentService при
`APP_ENV=development` и `YOO_MODE=test`:

```bash
backup_dir="$HOME/payment-service-backups"
install -d -m 700 "$backup_dir"
.venv/bin/python -m scripts.check_backup "$backup_dir"
```

`scripts.check_backup` создаёт дамп через контейнер
`botconstructorbackend-db-1`, копирует его в указанный каталог, восстанавливает
в новую базу с уникальным именем, сверяет операции с тестовой ЮKassa только
GET-запросами и удаляет временную базу. Дамп остаётся в каталоге backup. Для
другого контейнера или административной роли задайте `--container` и
`--admin-user`. При `Verification: ... unresolved` проверьте перечисленные ID:
команда завершится с кодом `1`. Создания платежей или возвратов в ЮKassa при
проверке нет.

Для регулярного копирования нужен отдельный backup runner с `pg_dump` той же
основной версии, что PostgreSQL. Каждый час запускайте
`.venv/bin/python -m scripts.backup_postgres /protected/payment-service-backups`.
Каталог должен существовать, находиться вне проекта и быть доступен только
учётной записи backup runner. Скрипт атомарно создаёт дамп в формате `custom`,
не передаёт пароль в аргументах процесса и удаляет локальные копии старше
14 дней. Успешные копии переносите в зашифрованное хранилище вне хоста БД с
версионированием и хранением 30 дней. Запись разрешайте только backup runner,
чтение — ограниченной группе восстановления. Настройте оповещение об ошибке
копирования или пропущенном запуске. Раз в месяц восстанавливайте свежую копию
в отдельной среде и измеряйте время до готовности сервиса. Дампы не храните в
Git или каталоге приложения.

Целевые показатели после настройки production-инфраструктуры: RPO не более
1 часа, RTO не более 4 часов. Они пока не подтверждены измерением в production.

### После потери БД

1. Остановите создание платежей, возвратов, плановую сверку и доставку событий. Не запускайте пустую БД вместо утраченной: это потеряет ключи идемпотентности и связь с операциями ЮKassa.
2. Выберите последний успешно скопированный дамп и зафиксируйте его время. Создайте отдельную пустую базу с владельцем `payment_service`. Восстановите её под этой ролью:

   ```bash
   pg_restore --no-owner --no-acl --exit-on-error --dbname="$restore_db" "$backup_file"
   ```

   Если подключается администратор, добавьте `--role=payment_service`. Не восстанавливайте поверх действующей БД.
3. Проверьте `alembic_version`, количество записей `payments`, `refunds`, `outbox_events` и связи между ними. Если доступен исходный снимок или его контрольные суммы, сравните строки. Оплаченные периоды хранятся в Backend и проверяются отдельно.
4. Для тестового магазина запустите `.venv/bin/python -m scripts.verify_restore "$restore_db"`. Скрипт только читает БД и делает GET-запросы к ЮKassa. Для другой среды задайте `RESTORE_DATABASE_URL` через секретное окружение. `mismatch`, `provider_unavailable` и `unverifiable_no_provider_id` требуют ручного разбора; новую операцию автоматически не создавайте. Для live-магазина нужна отдельная процедура с доступом оператора к кабинету ЮKassa.
5. После проверки переключите `DATABASE_URL` приложения на восстановленную базу, проверьте `/health/ready`, затем возобновите сверку и доставку outbox. Повторы событий безопасны только при идемпотентном Backend. Новые платежи и возвраты разрешайте после разбора неоднозначных операций.

Если ЮKassa недоступна, сохраняйте локальные `pending` и `unknown` без ручного
изменения статуса. После потери БД не возобновляйте создание операций до
сверки с провайдером. Оставьте webhook endpoint доступным для повторной
доставки: пока API ЮKassa недоступно, проверка ответит `503`. После
восстановления связи запустите сверку платежей и возвратов отдельно и разберите
`manual_review`.

Пробное восстановление 2026-11-05: дамп локального PostgreSQL 17 был скопирован
вне контейнера и восстановлен в отдельную базу. Схема `0007_observability`,
6 платежей, 1 возврат и 2 события outbox совпали с исходной БД по контрольным
суммам; наблюдаемая потеря операций в этом испытании — 0. Первый прогон сверки
со старыми тестовыми записями дал `7 unresolved`. После создания новой выборки
повторный `scripts.check_backup` завершился `Verification: matched` для
**5 платежей и 2 возвратов**, временная база удалена. Проверка выполняла только GET-запросы к ЮKassa, повторных
списаний не было. Сам `pg_restore` в первом испытании занял около 0,3 с;
полное RTO до готовности сервиса и фактические production RPO/RTO не измерены.

## Сборка и развёртывание стенда (шаг 6.4)

Нужны Docker с Compose, публичный DNS `PAYMENT_DOMAIN`, доступные порты 80/443
для выдачи сертификата Caddy и отдельная сеть Docker для доверенного Backend.
Внутренний HTTP API доступен только контейнерам этой сети по
`http://app:8002`; наружу Caddy пропускает лишь webhook и health.
PostgreSQL не публикует порт хоста. Секреты не входят в образ.

На чистом хосте скопируйте исходники выбранного коммита. Создайте сеть и
защищённый файл `.deploy.env` в каталоге проекта (`chmod 600 .deploy.env`).
В него запишите `PAYMENT_DOMAIN`, `PAYMENT_IMAGE=payment-service:<версия>`,
`POSTGRES_PASSWORD`, `DATABASE_URL=postgresql+asyncpg://payment_service:<тот же пароль>@db:5432/payment_service`,
`YOO_MODE=test`, `YOO_TEST_SHOP_ID`, `YOO_TEST_SECRET_KEY`,
`PAYMENT_RETURN_URL`, `BACKEND_TOKEN`, `ADMIN_TOKEN`, `BACKEND_BASE_URL`,
`ORDER_LOOKUP_TOKEN`, `PAYMENT_EVENT_TOKEN`. Для live-магазина используйте
`YOO_MODE=live` и рабочие реквизиты только после допуска этапа 7.3.
Backend должен видеть сервис в сети `payment-billing`; его адрес и токены
должны соответствовать этому файлу. `BACKEND_BASE_URL` в production использует HTTPS.
Пароль в URL кодируйте как компонент URI. Не коммитьте файл и не передавайте
его в журнал сборки. Для production предпочтительно передать те же переменные
через секреты оркестратора; Compose здесь описывает стенд.

```bash
docker network create payment-billing
docker build -t payment-service:<версия> .
docker scout cves payment-service:<версия>
docker compose --env-file .deploy.env -f compose.deploy.yaml config --quiet
docker compose --env-file .deploy.env -f compose.deploy.yaml up -d db
docker compose --env-file .deploy.env -f compose.deploy.yaml run --rm migrate
docker compose --env-file .deploy.env -f compose.deploy.yaml up -d app proxy
curl --fail https://<PAYMENT_DOMAIN>/health/ready
```

После `docker scout cves` оцените найденные уязвимости и остановите выпуск
при неприемлемых критических/высоких находках. Обновление зависимостей
делайте вместе с `pyproject.toml` и `constraints.txt`, затем пересобирайте
образ. Для воспроизводимого релиза сохраняйте digest собранного образа и
используйте его как `PAYMENT_IMAGE` при развёртывании. Приложение работает
под UID 10001. Контейнер миграции запускается отдельно и завершается до
старта приложения; если миграция завершилась с ошибкой, **не запускайте**
`up -d app proxy`. Проверяйте stdout контейнеров и `/health/ready`.

Сетевой экран хоста открывает снаружи только 80/443. Сеть `payment-billing`
доступна только доверенным контейнерам Backend, PaymentService и прокси.
Не публикуйте порт 8002 или 5432. TLS завершается на Caddy; для первого
получения сертификата домен должен указывать на хост. Плановые команды
сверки и доставки событий запускайте отдельно по расписанию и сохраняйте их вывод.

### Откат

Перед релизом создайте и проверьте резервную копию по шагу 6.3. Сохраните
digest прежнего образа и версию схемы (`python -m payment_service.migrate current`).
Если новая версия приложения не работает, верните прежний `PAYMENT_IMAGE` и
запустите `up -d app`, затем проверьте `/health/ready` и бизнес-маршруты.
Это безопасно лишь при совместимости прежнего кода с новой схемой. Если
миграция несовместима, остановите приложение и работников, восстановите
предрелизный дамп **в отдельную базу** по процедуре шага 6.3 и сверяйте
операции с ЮKassa перед возобновлением приёма запросов. Данные после момента
копии могут отсутствовать: не создавайте новые платежи до разбора расхождений.

Приёмка развёртывания и отката требует работающего Docker, DNS и тестового
Backend; проверки с обращением к ЮKassa выполняет оператор вручную.

## Инструкция оператору (шаг 6.5)

Работайте с локальным UUID платежа или возврата, а не с данными клиента.
В контейнерном стенде команды ниже запускаются как
`docker compose --env-file .deploy.env -f compose.deploy.yaml exec app python -m <модуль> <аргументы>`;
при локальном запуске с активированным `.venv` используйте `python -m`
(в Windows без активации — `.venv/Scripts/python.exe -m`).
Вывод и JSON-журнал `payment_service.operations` (это имя логгера, команда
`python -m payment_service.operations` не существует) сохраняйте в защищённом
журнале инцидента. Не записывайте туда токены, реквизиты, тело webhook и
персональные данные. Каждое ручное действие фиксируйте в журнале инцидента:
время UTC, оператор, номер обращения, тип и локальный ID операции, ID ЮKassa,
наблюдаемые статусы/суммы до и после, источник проверки, выполненная команда,
её результат и решение. Автоматический журнал операций не заменяет эту запись.

### Поиск и сверка операции

1. Для платежа с `unknown` запустите
   `python -m payment_service.reconcile` без ID:
   команда покажет локальный ID, ID ЮKassa (если есть), время первой попытки и
   число попыток сверки. Для всех `pending` платежей, включая пропущенные
   webhook, используйте `payment_service.reconcile --run` и найдите ID в выводе.
   Для возврата `payment_service.reconcile_refunds` без ID перечисляет все
   `pending` возвраты. Метрики `/internal/metrics` с `ADMIN_TOKEN` показывают
   возраст операций, отставание сверки и число неразрешённых расхождений.
2. Зафиксируйте исходное состояние и запустите сверку одного ID:
   `payment_service.reconcile <payment_id>` или
   `payment_service.reconcile_refunds <refund_id>`. Эти команды обращаются к
   ЮKassa; оператор запускает их сам. Сверьте результат с записью в кабинете
   ЮKassa и сохраните его в журнале инцидента.
3. `resolved` означает, что ответ ЮKassa обработан и локальная неопределённость
   снята; платёж при этом может оставаться `pending`, пока покупатель не завершит
   оплату. Команда печатает `outcome`, сохранённые `status` и `resolution_status`.
   При необходимости проверьте статус через `GET /payments/{id}` или `GET /refunds/{id}` с соответствующим
   служебным токеном. `known` означает совпадение уже завершённой операции.
   `unknown` означает недоступность API ЮKassa: повторите позже.
   `rate_limited` означает, что нужно подождать не менее минуты.
   `not_found` означает ошибочный локальный ID. `manual_review` оставляет
   запись среди неразрешённых расхождений: не меняйте статус вручную.

### Что делать по типу инцидента

| Случай | Действие |
| --- | --- |
| `pending` дольше 15 минут или `unknown` дольше 5 минут | Проверьте доступность ЮKassa и запуск плановой сверки. Сверьте конкретный ID. Если ID ЮKassa неизвестен, команда может повторить создание **только с исходным ключом** в течение 24 часов и в пределах пяти попыток. После окна — ручной разбор в кабинете; не создавайте новый платёж или возврат с новым ключом. |
| Сумма, валюта, ID ЮKassa или связь возврата с платежом не совпадает | Зафиксируйте локальные и подтверждённые в кабинете значения, отметьте `manual_review`, остановите дальнейшие действия по этой операции и передайте инцидент ответственному. Не исправляйте сумму или конечный статус прямым SQL. |
| Пропал webhook | Проверьте публичный HTTPS endpoint, подписку и историю доставки ЮKassa. Запустите сверку платежа и отдельно возврата, если он есть. После подтверждённого конечного статуса проверьте доставку события Backend через `payment_service.deliver_events`; при `--review` разберите событие с ответом `409` по `event_id` и заказу. Повторная доставка допустима только при идемпотентном Backend. |
| Спорный возврат | Проверьте исходный платёж, сумму и ID возврата в кабинете. Сверьте `refund_id`; пока возврат `pending` или `unknown`, доступ Backend не меняйте. При `manual_review` или несовпадении не создавайте второй возврат. После подтверждённого `succeeded` проверьте доставку `refund.succeeded` и изменение именно купленного периода в Backend. |

После разрешения инцидента запишите итог и время проверки. Для тестового
прогона другой оператор может взять ID из списка `unknown`, выполнить сверку
одного ID и приложить её вывод к журналу. Если подходящей записи нет,
`python -m scripts.test_yookassa create-unknown 10000` создаст платёж в
**тестовом** магазине и оставит локальную запись `pending + unknown`, как при
потере ответа после создания. Команда также покажет ссылку подтверждения для
ручной тестовой оплаты, но не сохранит ответ провайдера в БД. Сохраните выведенный `Payment ID` и вручную
запустите `python -m payment_service.reconcile <Payment ID>` в течение 24 часов.
Для этой команды нужны `APP_ENV=development`, `YOO_MODE=test` и реквизиты
тестового магазина; она обращается к ЮKassa и выполняется только оператором.
После сверки `python -m scripts.test_yookassa payment-status <Payment ID>`
покажет сохранённую ссылку подтверждения, пока платёж `pending`. Откройте её,
завершите оплату тестовой картой из документации ЮKassa и снова проверьте
`payment-status`. Без публичного webhook статус обновится при этом запросе;
для проверки сценария пропущенного webhook используйте вместо него
`python -m payment_service.reconcile <Payment ID>`. Тестовый магазин не
списывает настоящие деньги.

### Текущий статус приёмки шагов 6.4 и 6.5

На 2026-11-05 оба шага подготовлены, но **полная приёмка не проведена**.
Для 6.4 проверена конфигурация Compose; сборка и запуск стенда с чистого хоста,
сканирование уязвимостей образа, остановка релиза при ошибке миграции,
откат приложения и восстановление БД в целевой среде ещё не проверены.
Локально сейчас нет доступа к Docker Engine, публичному DNS и тестовому Backend,
поэтому эти испытания отложены до появления стенда.

Для 6.5 оператор вручную создал тестовый `pending + unknown` платёж, сверил его
и подтвердил итоговый `succeeded` в тестовом магазине. Независимый прогон
инструкции другим разработчиком и запись его действий в защищённый журнал
инцидента ещё не выполнены; отдельного механизма аудита ручных действий
в сервисе нет. Эти проверки также остаются открытыми до доступности
подходящей среды и второго оператора.

## Проверка в тестовом магазине без Backend

Укажите в локальном `.env` `APP_ENV=development`, `YOO_MODE=test`, `DATABASE_URL`, `YOO_TEST_SHOP_ID`, `YOO_TEST_SECRET_KEY` и `PAYMENT_RETURN_URL`. Примените миграции. Скрипт работает только с тестовым магазином и создаёт локальный тестовый заказ в БД PaymentService; Backend не вызывается.

```bash
.venv/bin/python -m payment_service.migrate upgrade
.venv/bin/python -m scripts.test_yookassa create 10000
# Откройте выведенный Confirmation URL и оплатите тестовой картой.
payment_id="UUID из строки Payment ID"
.venv/bin/python -m scripts.test_yookassa payment-status "$payment_id"
.venv/bin/python -m scripts.test_yookassa refund "$payment_id"
refund_id="UUID из строки Refund ID"
.venv/bin/python -m scripts.test_yookassa refund-status "$refund_id"
```

Если последний статус ещё `pending`, повторите `refund-status` спустя минуту. Возврат считается завершённым только при `succeeded`. Тестовые платежи создают события в outbox; без Backend не запускайте доставку этих событий.

Проверка платежа и возврата через этот скрипт с тестовым магазином ЮKassa выполнена успешно. Сквозной сценарий с реальным BotConstructorBackend ещё не проверяли: проверку роли администратора в Backend, создание платежа по его заказу и применение события о возврате к оплаченному периоду нужно проверить при интеграции сервисов.
